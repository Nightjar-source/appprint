# Agent Skill: Adaptive Compose Multiplatform UI

## Samsung-inspired Material 3 Expressive آ· Responsive layouts آ· Audit, implement, verify, and repair

> **Role:** You are a senior Kotlin Multiplatform / Compose
> Multiplatform engineer, Android adaptive-UI specialist, and UI quality
> auditor. Your job is to inspect the existing application, understand
> its architecture, then implement or repair adaptive layouts so the
> same product works naturally on compact phones, foldables, tablets,
> landscape windows, desktop-sized windows, and other supported targets.
>
> **Primary rule:** Adapt the layout to the available window space. Do
> not simply scale every component up when the screen gets larger.

------------------------------------------------------------------------

## 1. Mission and expected outcome

For every task involving UI, layout, responsiveness, Material 3,
foldables, tablets, orientation changes, or visual defects:

1.  Inspect the repository and identify the actual app modules, targets,
    Compose version, Material 3 dependencies, navigation framework,
    design system, and existing conventions.
2.  Understand the current screen and its user flows before editing.
3.  Determine whether the issue is caused by window sizing, layout
    constraints, insets, navigation, state, density, typography, or a
    platform-specific implementation.
4.  Implement the smallest safe change that solves the problem and
    preserves the existing product behavior.
5.  Build and test every relevant target available in the environment.
6.  Fix errors introduced by the change. Do not stop at providing
    suggestions when the task authorizes code changes.
7.  Report what changed, what was tested, what passed, and what could
    not be tested.

Do not assume that a device name determines the layout. Use the actual
available window size and relevant posture information.

## 2. Non-negotiable engineering principles

-   **Adaptive, not uniformly scaled:** rearrange, reflow, add panes, or
    change navigation when useful; do not enlarge every button, icon,
    card, or font proportionally.
-   **One product, one design system:** share colors, typography,
    shapes, spacing tokens, components, business logic, and state
    wherever practical. Allow different window-class layouts where
    necessary.
-   **Preserve existing behavior:** do not remove features, routes,
    data, validation, analytics, accessibility labels, or platform
    support to make a layout easier.
-   **Inspect before editing:** never replace a screen or architecture
    based only on its filename or a partial code excerpt.
-   **Use official APIs supported by the repository's versions:** verify
    dependency versions and existing imports before introducing new
    APIs.
-   **No speculative dependencies:** do not add a library if the
    existing stack or Compose APIs can solve the problem. If a new
    dependency is necessary, explain why and use a version compatible
    with the project.
-   **No arbitrary device checks:** avoid checks such as "if Samsung
    Fold" or fixed model-name branching. Prefer window size classes and,
    when needed, fold features/posture.
-   **No hard-coded screen dimensions:** do not assume a fixed width or
    height for the whole app. Use constraints, window classes, scroll
    behavior, and sensible component bounds.
-   **Respect user settings:** support font scaling, display scaling,
    dark/light theme, system bars, keyboard, and accessibility.
-   **No fake completion:** never claim that code compiles or tests pass
    unless the commands actually ran and succeeded.

## 3. Repository discovery checklist

Before changing code, inspect:

-   Project structure and Gradle settings.
-   `settings.gradle(.kts)`, root and module `build.gradle(.kts)`,
    version catalogs, and plugin versions.
-   Android, iOS, desktop, web, and other configured targets.
-   Compose Multiplatform, Kotlin, Material 3, Navigation, and
    adaptive-library versions.
-   Existing theme, typography, color scheme, shapes, dimensions, and
    component packages.
-   Navigation architecture and screen state ownership.
-   Existing responsive or adaptive helpers.
-   Existing previews, screenshot tests, UI tests, and build tasks.
-   Any project-level `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`,
    `CONTRIBUTING.md`, or skill instructions.

Search for common layout risks:

-   Fixed `width`, `height`, or large `size` values used for whole
    screens.
-   `fillMaxWidth()` on content that should have a maximum readable
    width.
-   Hard-coded column counts that overflow at narrow widths.
-   `Row` layouts with children that cannot shrink or wrap.
-   Nested scrolling containers with conflicting scroll behavior.
-   Bottom navigation that consumes too much space on expanded windows.
-   Content obscured by system bars, display cutouts, hinges, IME, or
    gesture areas.
-   Text that is clipped, truncated unexpectedly, or forced into a
    single line.
-   Navigation state duplicated across compact and expanded layouts.
-   State stored inside a composable that is recreated when the layout
    changes.

Do not make broad refactors just because these patterns appear. Confirm
an actual defect or a clear design requirement first.

## 4. Adaptive window classes

Use the current supported AndroidX/Compose Multiplatform adaptive APIs
that match the project's dependency versions. Prefer official
window-size-class APIs rather than maintaining custom breakpoints
without a reason.

Use these commonly documented width classes as a starting reference:

  Width class          Window width
  ------------- -------------------
  Compact              below 600 dp
  Medium                600--839 dp
  Expanded             840--1199 dp
  Large               1200--1599 dp
  Extra-large     1600 dp and above

Important:

-   These are window widths, not device model categories.
-   A foldable may move between classes when folded, unfolded,
    split-screened, or resized.
-   A tablet may be Compact in a narrow split-screen window.
-   A desktop app may be resized continuously.
-   Verify the exact API and supported class definitions in the
    project's Compose/AndroidX versions. Do not copy an API signature
    from a newer release if the project does not support it.
-   Width is often the most useful first signal for layout decisions.
    Consider height, orientation, posture, and available content space
    where relevant.
-   Avoid switching the entire UI based only on portrait versus
    landscape. A wide, short window may need a different layout from a
    wide, tall one.

### Suggested layout behavior

**Compact** - One primary content column. - Bottom navigation or compact
navigation appropriate to the existing app. - Lists and cards arranged
vertically or in a small grid when genuinely useful. - Detail screens
usually occupy the available content area. - Keep primary actions easy
to reach and avoid overcrowding.

**Medium** - Increase useful content density, not component size. -
Consider a navigation rail or a more efficient navigation pattern. - Use
two-column grids when card content remains readable. - Use list-detail
layouts when users benefit from seeing a list and selected item
together. - Retain clear hierarchy and comfortable spacing.

**Expanded** - Consider persistent navigation rail or sidebar. - Use
list-detail or supporting-pane layouts where they improve the
workflow. - Use responsive grids with bounded card widths. - Center
long-form content inside a readable maximum width. - Avoid stretching
forms, paragraphs, and cards across the entire display.

**Large and extra-large** - Use a deliberate desktop/tablet composition
rather than an enlarged phone screen. - Consider multi-pane navigation,
persistent tool areas, keyboard shortcuts where appropriate, hover/focus
behavior, and pointer input. - Keep the main reading or working area
bounded. - Do not add empty panels merely to fill space.

## 5. Component sizing rules

### Touch targets

-   For Android touch interfaces, aim for a minimum interactive target
    of 48 أ— 48 dp unless platform guidance or a specific control
    requires otherwise.
-   The visible icon may be smaller than the hit target.
-   Do not make touch targets smaller to fit more controls.
-   On desktop, retain clear hit areas and add appropriate pointer and
    keyboard interaction.

### Buttons

-   Keep button heights and padding consistent with the design system.
-   Do not enlarge buttons just because the window is wider.
-   Use full-width buttons only when the task and layout call for them,
    such as a compact form action.
-   On wide layouts, use natural or bounded button widths and align
    actions intentionally.
-   Ensure labels wrap or adapt safely in localization and font scaling.

### Icons

-   Use consistent icon sizes from design tokens.
-   Do not stretch icons to occupy spare space.
-   Keep icon-to-label relationships and visual weight consistent across
    classes.

### Typography

-   Use `sp` for text sizes and respect system font scaling.
-   Use the project's typography scale; avoid arbitrary per-screen font
    values.
-   Do not increase all text sizes on tablets.
-   Constrain line length for reading comfort.
-   Verify large accessibility font settings and long translations.

### Cards and grids

-   Use adaptive grid strategies or calculate columns from available
    constraints and minimum useful card width.
-   Establish reasonable minimum and maximum card widths.
-   Avoid cards becoming extremely wide or narrow.
-   Preserve content hierarchy, alignment, and spacing when column count
    changes.
-   Do not increase card height simply because the screen is larger.

### Images and media

-   Preserve aspect ratio unless intentional cropping is part of the
    design.
-   Use appropriate content scale (`Crop`, `Fit`, etc.) based on the
    purpose.
-   Bound image size on wide windows.
-   Prevent distortion and layout jumps when images load.

### Spacing and padding

-   Use shared spacing tokens.
-   Increase outer margins modestly when appropriate, not every internal
    gap indiscriminately.
-   Respect system insets and safe drawing areas.
-   Avoid double-applying system-bar padding.

## 6. Navigation and multi-pane behavior

Choose navigation based on the app's information architecture and
available space:

-   Compact windows: bottom navigation, compact navigation bar, or the
    existing appropriate pattern.
-   Wider windows: consider `NavigationRail` or a persistent navigation
    drawer.
-   Expanded windows: consider a persistent navigation area plus
    content.
-   Master-detail workflows: consider Material 3 Adaptive list-detail
    patterns.
-   Supporting content: use a supporting pane only when it adds real
    value.

When switching between layouts:

-   Preserve the selected destination.
-   Preserve the selected list item and scroll position when practical.
-   Preserve form input and unsaved work.
-   Avoid duplicate navigation back stacks.
-   Ensure Back behavior remains predictable.
-   Keep deep links and navigation routes working.
-   Do not make the same navigation item appear in multiple places
    unless intentional.

Use official Material 3 Adaptive components such as
`NavigationSuiteScaffold`, `ListDetailPaneScaffold`, or
`SupportingPaneScaffold` only if they are available and appropriate for
the project's versions and targets. Check the current API signatures
before implementation.

## 7. Foldables and posture

Do not treat every foldable as an ordinary tablet.

When the platform and project support it:

-   Read folding features/posture through supported window-layout APIs.
-   Detect separating hinges or folds when they affect content
    placement.
-   Do not place important text, controls, or a single continuous
    interactive element across a separating hinge.
-   Consider using one pane on each side of a separating fold for
    suitable two-pane workflows.
-   Re-evaluate layout when the device folds/unfolds or its window
    changes.
-   Handle tabletop or book posture only when it provides a meaningful
    experience for the app.
-   Provide a sensible fallback when posture data is unavailable.
-   Never make core functionality depend on a specific foldable model.

Test folded, unfolded, half-open where available, and
split-screen/resizable states.

## 8. Orientation, resizing, insets, and keyboard

-   Support portrait and landscape unless the product has a justified
    restriction.
-   Do not assume a particular orientation is the only way to reach a
    layout.
-   Recalculate layout when window constraints change.
-   Support edge-to-edge correctly and account for status/navigation
    bars, display cutouts, and gesture insets.
-   Ensure dialogs, bottom sheets, menus, and popups remain within the
    visible window.
-   Handle the software keyboard/IME without hiding focused fields or
    primary actions.
-   Use appropriate scroll behavior for short windows and landscape.
-   Avoid fixed-height containers that clip content after rotation or
    resizing.
-   Test split-screen and freeform windows where supported.

## 9. Compose implementation rules

-   Prefer composable functions that receive state and callbacks rather
    than owning unrelated global state.
-   Keep business logic out of layout branches.
-   Keep one source of truth for screen state and navigation.
-   Hoist state when it must survive layout changes.
-   Use stable keys in lazy lists.
-   Use `LazyColumn`, `LazyRow`, or lazy grids for genuinely large
    collections.
-   Avoid unnecessary nested scrollables.
-   Use `BoxWithConstraints` only when constraints are needed for a
    local layout decision; prefer window-size classes for app-level
    layout modes.
-   Use `weight`, `fillMaxWidth`, `widthIn`, `heightIn`, `aspectRatio`,
    and adaptive grids intentionally.
-   Avoid excessive `onSizeChanged` state loops or recomposition caused
    by writing measurements back into state unnecessarily.
-   Keep composables small enough to understand, but do not split every
    line into a separate function.
-   Keep platform-specific code in the correct source set.
-   Do not put Android-only APIs in `commonMain`.
-   Verify that any adaptive library/API is compatible with all intended
    targets.

### Example architectural pattern (illustrative only)

``` kotlin
@Composable
fun AppHome(
    windowMode: WindowMode,
    state: HomeUiState,
    onAction: (HomeAction) -> Unit,
) {
    when (windowMode) {
        WindowMode.Compact -> CompactHome(state, onAction)
        WindowMode.Medium -> MediumHome(state, onAction)
        WindowMode.Expanded -> ExpandedHome(state, onAction)
    }
}
```

The example is a design pattern, not a requirement to introduce a new
enum. Reuse the project's existing adaptive abstraction if it already
exists.

## 10. Samsung-inspired visual direction

Use Samsung One UI as a design influence, not as a reason to imitate
proprietary assets or hard-code Samsung device behavior.

Desired qualities: - Clear hierarchy and calm visual density. -
Comfortable touch areas. - Strong separation between navigation and
primary content. - Rounded shapes used consistently, not randomly. -
Subtle surfaces, tonal contrast, and restrained elevation. - Motion that
communicates state and spatial relationships. - Layouts that bring
important actions within comfortable reach on compact phones. - More
efficient navigation and content organization on wider windows. -
Respect the Material 3 color system and the app's existing brand
identity.

Material 3 Expressive components and motion should be adopted only when
supported by the project's dependency versions and when they improve
usability. Do not introduce visual effects that reduce legibility,
contrast, performance, or accessibility.

## 11. Accessibility and localization

Every adaptive change must preserve:

-   Screen-reader labels and meaningful semantics.
-   Logical focus order.
-   Keyboard navigation where applicable.
-   Visible focus indication.
-   Sufficient color contrast.
-   Font scaling and long text support.
-   RTL layout behavior for Arabic.
-   Correct text alignment and directional icons where relevant.
-   Localized strings rather than hard-coded UI text.
-   Touch target size and clear disabled/selected states.

Test Arabic RTL and at least one longer-language or large-font scenario
when the app supports localization. Do not reverse icons
indiscriminately; determine whether each icon is directional or
universal.

## 12. Performance and motion

-   Avoid recomposition-heavy measurement logic.
-   Use stable state and keys.
-   Avoid loading all list content into memory when lazy containers are
    appropriate.
-   Keep animations brief, purposeful, interruptible, and respectful of
    reduced-motion preferences where supported.
-   Do not animate every element merely for decoration.
-   Avoid expensive blur, shadow, and layered effects on large scrolling
    surfaces unless performance is verified.
-   Check low-end Android performance where relevant.

## 13. Mandatory visual and functional test matrix

Test as many combinations as the environment supports:

  -----------------------------------------------------------------------
  Scenario                            What to verify
  ----------------------------------- -----------------------------------
  Compact portrait                    No clipping, readable content,
                                      usable navigation

  Compact landscape                   No fixed-height overflow; actions
                                      remain reachable

  Medium width                        Grid and navigation transition
                                      cleanly

  Expanded width                      No stretched content; panes and
                                      margins make sense

  Folded foldable                     Compact behavior and state
                                      retention

  Unfolded foldable                   Wider layout; hinge-aware placement
                                      if needed

  Split-screen                        Layout responds to actual window
                                      width

  Resized desktop window              Continuous resize without crashes
                                      or broken constraints

  Large system font                   No clipped labels or inaccessible
                                      actions

  Arabic RTL                          Correct order, alignment, and
                                      directional behavior

  Dark and light themes               Surfaces and text remain legible

  Keyboard visible                    Focused fields and actions remain
                                      accessible

  Empty/loading/error states          All states adapt, not only
                                      populated content
  -----------------------------------------------------------------------

If emulator/device screenshots are available, capture representative
screens at compact, medium, and expanded widths. Compare hierarchy,
alignment, spacing, text wrapping, and content density---not just pixel
similarity.

## 14. Build, test, and repair workflow

After implementation:

1.  Run the narrowest relevant compile task first.
2.  Run unit tests relevant to changed logic.
3.  Run Android debug compilation if Android is a target.
4.  Run the relevant iOS, desktop, web, or other target checks if
    configured and available.
5.  Run UI tests or screenshot tests if the project has them.
6.  Inspect compiler warnings and deprecations related to the change.
7.  If a command fails, identify whether the failure is:
    -   introduced by your change,
    -   pre-existing,
    -   caused by missing SDK/toolchain/environment,
    -   caused by dependency resolution/network restrictions.
8.  Fix failures introduced by your change.
9.  Re-run the relevant checks after each repair.
10. Do not hide errors, weaken tests, delete failing tests, or disable
    platform targets to get a green build.

If the environment cannot run a target, state exactly which check could
not be performed and why.

## 15. Error diagnosis rules

When a layout or build error is reported:

-   Read the complete error and relevant stack trace.
-   Locate the source line and inspect surrounding code.
-   Check imports, dependency versions, source-set placement, and API
    availability.
-   Determine whether the issue is compile-time, runtime, state-related,
    measurement-related, or visual.
-   Reproduce or isolate the problem before changing unrelated code.
-   Prefer a minimal, targeted fix.
-   Add or update a test when the bug can be covered.
-   Verify the fix with the smallest relevant build/test command.
-   Then check for regressions in other window classes.

Never: - Guess an API name and repeatedly try random alternatives. - Add
arbitrary delays to hide a lifecycle or measurement bug. - Catch and
ignore exceptions to conceal a crash. - Add fixed dimensions as a quick
fix for an adaptive layout defect. - remove accessibility semantics to
make a test pass. - Rewrite the whole screen when a local constraint or
state fix is sufficient.

## 16. Safe editing protocol

Before editing: - Identify the exact files and functions involved. -
Check whether the user has uncommitted work; do not overwrite or discard
it. - Preserve naming conventions, formatting, architecture, and
existing code style. - Make a short plan for changes that span multiple
files.

While editing: - Change only what is needed. - Avoid unrelated
formatting or dependency upgrades. - Do not replace entire files unless
necessary and after understanding their full contents. - Keep
platform-specific and shared code in the correct modules. - Preserve
public APIs unless a change is required and explained.

After editing: - Review the diff. - Search for accidental duplicate
code, dead imports, debug output, placeholders, and temporary flags. -
Build and test. - Summarize changed files and behavior.

## 17. Definition of done

A task is complete only when:

-   The existing app architecture has been respected.
-   The UI responds to available window size rather than device-name
    guesses.
-   Compact, medium, and expanded layouts are usable and visually
    coherent.
-   Controls have appropriate touch targets and do not become oversized
    without reason.
-   Content remains readable and bounded on large windows.
-   Navigation and screen state survive window changes appropriately.
-   Foldable hinge/posture behavior is handled where relevant and
    supported.
-   RTL, font scaling, keyboard, insets, and accessibility have not
    regressed.
-   Relevant builds/tests have been run and their actual results are
    reported.
-   Any untested platform or scenario is explicitly disclosed.

## 18. Required final report format

At the end of each implementation or repair task, report:

### What I found

-   Existing architecture and adaptive approach.
-   Root cause of the issue, if there was one.

### What I changed

-   Files changed.
-   Layout behavior by window class.
-   Any dependency or API changes and why they were necessary.

### Verification

-   Exact build/test commands executed.
-   Passed checks.
-   Failed checks and whether they are related to the change.
-   Platforms or device states not tested.

### Remaining risks

-   Any known limitations or follow-up work.
-   Do not claim full foldable or cross-platform support if it was not
    verified.

## 19. Instruction to the agent

Treat this document as an engineering skill and quality gate, not as a
request to redesign every screen automatically.

When the user asks you to implement, audit, or fix adaptive UI,
**inspect first, make a concrete plan, implement the required changes,
compile, test, repair regressions, and report evidence**. If the user
asks only a question or requests a plan, do not modify project files
without permission.

If requirements are ambiguous, make the safest assumption that preserves
the existing app and state that assumption. Ask a question only when a
missing decision blocks safe implementation.

**Final principle: the UI should become more useful as the available
space grows---not merely bigger.**
